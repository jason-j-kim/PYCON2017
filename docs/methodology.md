# AI 평가·문답 시스템 설계 원칙과 개발 과정

*이 프로젝트(소크라테스식 아이디어·정책 평가)에서 확립한 원칙을 다른 앱에 재사용하기 위한 문서.*

---

## 1. 이 시스템이 무엇을 하는가

소크라테스 문답으로 아이디어(정책)의 가치를 **제안자가 스스로 입증**하게 하고,
AI가 **이원 채점**으로 설득력 있게 평가한다. AI는 아이디어를 칭찬하거나 대신
결론 내리지 않는다 — 질문을 던지고, 답변에서 가치가 드러나게 한다.

---

## 2. 핵심 설계 원칙 (다른 앱에도 그대로 적용 가능)

### 2.1 평가 철학

- **P1. AI는 판단을 강요하지 않고 질문으로 드러낸다.** 문답 단계에서 질문자는
  채점을 언급하지 않는다.
- **P2. 설득력 있는 채점 = 이원 채점.** 기계적 체크리스트(사실 판정)와 종합
  인상 채점을 각각 구하고 그 평균을 쓴다. 한쪽만으로는 "왜 그 점수냐"에 방어가
  안 된다.
- **P3. 모든 하위 점수는 근거(대화 턴) 인용을 요구한다.** 인용이 없으면 자동으로
  불충족 처리 → 말로 얼버무리는 답변을 걸러낸다.
- **P4. 채점 기준은 이론에 근거한다.** (예: Rogers 확산이론 5속성, Davis TAM,
  Real-Win-Worth, Lean MVP.) 임의로 만든 기준은 외부 연구자에게 반박당한다.

### 2.2 구조와 역할 분리

- **P5. 질문자와 채점자를 분리한다.** 질문자는 점수를 모르고, 채점자는 대화에
  참여하지 않고 로그만 본다. 역할 오염을 막는다.
- **P6. 흐름은 코드가 강제한다(상태 머신).** 단계 전이는 프로그램이 정하고,
  LLM에는 매 단계의 지시만 준다. 재현성과 공정성을 보장한다.
- **P7. 산술은 코드가 계산한다.** 가중 평균·환산 등은 LLM에 맡기지 않는다.

### 2.3 수정·확장 원칙 (원본을 지키며 개선)

- **P8. 기존 버전 무손상.** 새 기능은 ① 하위호환 인자(기본값=현행) ② 순수함수
  ③ 신규 파일 로만 얹는다. 공유 코드를 그 자리에서 갈아엎지 않는다.
- **P9. 프로필/모드 스위치로 버전을 공존시킨다** (파일 포크 대신). 기본값이 곧
  원본 보장이 된다.
- **P10. 추가 비용(AI 호출)을 최소화한다.** 표현 계층은 이미 나온 채점 결과로
  코드가 계산한다. **새 숫자를 만들지 말고, 기존 결과를 서술로 재조립**한다.

### 2.4 연구 타당성과 편향 방지

- **P11. 연구 세션은 조건을 고정한다** (가중치 등). 세션 간 점수 비교 가능성을
  확보한다.
- **P12. 참가자 화면에 모범답안·완성 예시를 두지 않는다.** 앵커링·게임화로
  데이터가 오염된다.
- **P13. 안내는 '내용'이 아니라 '태도'만 표준화한다** (모두에게 동일한 지침).
- **P14. 블라인드 — 참가자에게 점수·라벨을 비공개한다.**
- **P15. 데이터 저장·분석 동의를 고지한다.**

### 2.5 보안과 운영

- **P16. 비밀번호·키를 코드·저장소에 넣지 않는다.** 실행 시 입력받거나 환경
  변수로 준다.
- **P17. 외부 공개에는 안전장치를 둔다** (접속 코드, 일일 세션 상한).
- **P18. 공개 문서에서 내부 자원(저장소 주소 등)은 노출을 생략한다.**
- **P19. 구독 기반으로 외부에 서비스하는 것은 약관 회색지대다** — 소규모·단기
  테스트에만 쓰고, 지속 운영은 정식 경로로 전환한다.

## 3. 검증 방법론

- **시뮬레이션으로 판별력 검증** — 진부한 사례 vs 창의적 사례의 점수 격차,
  "길지만 내용 없는 답변" 같은 조작에 대한 내성.
- **다중 에이전트** — 제안자 / 질문자 / 채점자 2종(체크리스트·종합) / 재판장을
  분리해 서로 감시.
- **인간 심사위원 블라인드 교차검증** — AI 점수와 사람 점수의 일치도.
- **순수함수 단위 검증** — AI 호출 없이 계산 로직을 먼저 확인한다.
- **원본 무손상 회귀 검증** — 기본 설정으로 돌린 결과가 종전과 동일한지 확인.

## 4. 개발 과정 (작업 방식)

**단계:** 전략 수립 → 프롬프트 프로토타입(CLI) → 웹 MVP → 이원 채점 도입 →
시뮬레이션 검증 → 인간 심사 자료 → 공개 페이지 → 터널 배포 → 질문자 변형
실험·채택 → 수정판(정책).

**반복 규율:** 제안 → (실행 전) **평가** → 확인 → 구현 → 검증 → 커밋/푸시.

**핵심 습관 — "계획에 문제 없는지 먼저 판단한다."** 코딩에 들어가기 전에 결함·
범위·비용(특히 추가 호출)을 짚는다. 실행은 그다음이다.

## 5. 다른 앱에 적용할 때의 체크리스트

- [ ] 평가가 목적인가? 그렇다면 단일 채점 대신 **이원 채점**을 고려했는가?
- [ ] **질문자와 채점자를 분리**했는가?
- [ ] 흐름을 **코드로 강제**하고 산술을 **코드로 계산**하는가?
- [ ] 기준에 **이론적 근거**가 있고, **근거 인용**을 요구하는가?
- [ ] 기존 버전을 **무손상**으로 두고 **프로필**로 확장하는가?
- [ ] 새 출력은 **새 호출 없이** 기존 결과로 만들 수 있는가?
- [ ] 연구용이면 **조건을 고정**하고 **편향(예시·모범답안)**을 제거했는가?
- [ ] 비밀정보를 **코드 밖**에 두고, 외부 공개 **안전장치**가 있는가?
- [ ] **AI 호출 없이 검증**할 방법을 마련했는가?

---

## 6. 한 줄 요약

> **판단하지 말고 질문하라. 설득력은 이원 채점과 근거 인용에서 나온다.
> 원본은 지키고, 새것은 공짜로(추가 호출 없이) 얹어라. 연구는 조건을 고정하고
> 편향을 제거하라.**
