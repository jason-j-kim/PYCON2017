# 소크라테스 문답법 기반 AI 아이디어 평가 시스템 — 구현 전략

## 1. 핵심 철학: 입증 책임의 전환

기존 아이디어 평가 시스템은 "시스템이 심판"이 되는 구조다. 이 시스템은 반대로,
**제안자가 AI와의 대화를 통해 스스로 아이디어의 가치를 입증**하도록 설계한다.

- AI는 판결을 내리지 않는다. **질문만 한다.**
- 점수는 아이디어 자체가 아니라 **"제안자가 질문에 얼마나 잘 답했는가"**, 즉
  방어의 성실성과 논리적 견고함에서 나온다.
- 나쁜 아이디어는 AI가 지적해서 탈락하는 것이 아니라, 제안자가 답변 과정에서
  **스스로 결함을 깨닫고** 철회하거나 수정하게 된다.
- 좋은 아이디어는 문답을 통해 더 날카로워지고, AI는 격려와 개선 방향을 제시한다.

이 구조의 부수 효과: AI의 오판(할루시네이션) 리스크가 크게 줄어든다. AI가 "이
아이디어는 나쁘다"고 단정하는 순간이 없기 때문이다.

## 2. 평가 기준과 점수 체계

### 2.1 세 가지 기준

| 기준 | 정의 | 검증하는 질문의 방향 |
|------|------|---------------------|
| **독창성** (Originality) | 기존 해법과 얼마나 다른가, 새로운 관점이 있는가 | "비슷한 것이 이미 존재하지 않는가? 무엇이 다른가?" |
| **실용성** (Practicality) | 실제로 구현·실행 가능한가, 비용 대비 효과가 있는가 | "무엇이 필요한가? 가장 큰 장애물은? 최소 버전은?" |
| **수용태도** (Acceptance) | 대상 사용자·이해관계자가 받아들일 것인가 | "누가 쓰는가? 그들이 지금 방식을 버릴 이유는?" |

### 2.2 점수 산정 방식

각 기준을 0~10점으로 채점하되, 채점 대상은 **대화 로그 전체**다.

```
최종 점수 = w1·독창성 + w2·실용성 + w3·수용태도   (w1+w2+w3 = 1)
기본 가중치: w1 = 0.35, w2 = 0.35, w3 = 0.30
```

- 가중치는 세션 생성 시 관리자(교수/운영자)가 조정 가능하게 한다.
  (예: 연구 아이디어 공모라면 독창성 가중치를 올리고, 사내 개선 제안이라면
  실용성을 올린다.)
- 각 기준의 점수는 하위 지표의 합으로 산출해 설명 가능성을 확보한다:
  - **답변의 구체성**: 추상적 주장 대신 근거·사례·수치를 댔는가 (0~4)
  - **논리적 일관성**: 이전 답변과 모순되지 않는가, 반례에 대응했는가 (0~3)
  - **자기 인식**: 약점을 인정하고 개선안을 냈는가 (약점 인정은 감점이 아니라 **가점**) (0~3)
- "약점 인정 = 가점" 규칙이 핵심이다. 이것이 제안자가 방어적으로 거짓말하는
  대신 솔직하게 사고하도록 만드는 인센티브다.

## 3. 소크라테스 문답법의 현대적 적용 — 대화 설계

### 3.1 질문 유형 (AI가 사용하는 6가지 도구)

소크라테스의 논박술(elenchus)과 산파술(maieutics)을 현대적 질문 분류로 옮긴다.

1. **명료화** — "그 아이디어를 한 문장으로 다시 말하면? '많은 사람'은 구체적으로 누구인가?"
2. **전제 검증** — "그 주장은 X가 참이라는 가정 위에 서 있다. X가 거짓이면 어떻게 되는가?"
3. **근거 요구** — "그렇게 믿는 근거는 무엇인가? 직접 확인한 것인가, 추측인가?"
4. **관점 전환** — "경쟁자/반대자/비용을 대는 사람의 입장에서 보면 어떤가?"
5. **결과와 함의 탐색** — "성공하면 다음에 무슨 일이 일어나는가? 최악의 부작용은?"
6. **반례 제시** — "과거에 Y가 비슷한 시도를 했고 실패했다. 당신의 경우는 무엇이 다른가?"
   (유일하게 AI가 정보를 '제공'하는 유형. 단정이 아니라 반례+질문 형태로만.)

### 3.2 대화 흐름 (상태 머신)

```
[접수] 아이디어 제출 (자유 서술)
   ↓
[명료화] 1~2턴: 아이디어를 한 문장 정의로 압축시킨다.
   ↓         합의된 정의가 이후 모든 문답의 기준점이 된다.
[문답 라운드] 기준별 순회 (독창성 → 실용성 → 수용태도)
   │  각 기준당 2~4턴. 답변 품질에 따라 적응적으로:
   │   - 구체적 답변 → 다음 단계로 진행 + 짧은 인정 ("좋은 지적입니다")
   │   - 모호한 답변 → 같은 지점을 다른 각도로 재질문 (최대 2회)
   │   - 모순 발견 → 두 발언을 나란히 인용하고 해명을 요청
   ↓
[자기 평가] "지금까지의 대화를 바탕으로, 아이디어의 가장 큰 약점을
   ↓          스스로 꼽는다면?" — 자기 인식 점수의 핵심 측정 지점
[종합] 점수 + 근거(대화 인용) + 개선 제안 2~3개 + 격려
```

- 전체 세션은 **10~15턴, 15분 이내**로 제한한다. 무한 심문은 피로감만 준다.
- 상태 전이는 LLM의 자율 판단이 아니라 **서버 측 상태 머신이 강제**한다.
  LLM에게는 "지금은 실용성 라운드 2번째 질문" 같은 컨텍스트를 매 턴 주입한다.
  이래야 대화가 산으로 가지 않고 채점 근거도 기준별로 정렬된다.

### 3.3 어조 규칙 (격려와 개선)

- 심문이 아니라 **산파술**: "당신 안에 이미 있는 답을 꺼내는 것을 돕는다"는 태도.
- 매 라운드에서 잘한 답변은 반드시 구체적으로 인정한다. (막연한 칭찬 금지)
- 약점이 드러났을 때 AI가 결론을 대신 말하지 않는다. 제안자가 스스로 말할
  때까지 질문한다. 단, 2회 재질문 후에도 막히면 힌트를 주고 넘어간다.
  (좌절시키는 것이 목적이 아님)
- 종합 단계에서만 AI가 처음으로 '의견'을 말한다: 개선 제안과 격려.

## 4. 웹 시스템 아키텍처

웹 페이지로 충분히 구현 가능하며, MVP는 소규모로 만들 수 있다.

### 4.1 기술 스택 (제안)

```
프론트엔드   React (또는 순수 HTML+JS) — 채팅 UI + 결과 대시보드
백엔드       Python FastAPI — 세션/상태 머신/채점 파이프라인
LLM          Claude API (대화 생성 + 루브릭 채점, 두 역할 분리 호출)
DB           SQLite(MVP) → PostgreSQL — 세션, 대화 로그, 점수
스트리밍     SSE(Server-Sent Events) — 질문이 타이핑되듯 표시
```

이 저장소가 Python 기반이므로 백엔드는 Python으로 통일하는 것이 자연스럽다.

### 4.2 컴포넌트 구조

```
[브라우저 채팅 UI]
      │ REST + SSE
[FastAPI 서버]
  ├─ 세션 관리자: 상태 머신 (현재 단계, 라운드, 턴 수)
  ├─ 대화 엔진: "질문자 프롬프트" + 대화 이력 → 다음 질문 생성
  ├─ 채점 엔진: 대화 종료 후 "채점자 프롬프트" + 전체 로그 → 구조화된 점수
  └─ 저장소: idea, session, turn, evaluation 테이블
```

**질문자와 채점자를 별도 LLM 호출로 분리**하는 것이 중요하다.
- 질문자는 점수를 모른다 → 대화 중 편향된 유도 질문을 막는다.
- 채점자는 대화에 참여하지 않는다 → 로그만 보고 루브릭대로 채점한다.
- 채점은 JSON 스키마 강제(structured output)로 받아 파싱 오류를 없앤다.

### 4.3 데이터 모델 (최소)

```sql
idea       (id, title, description, author, created_at)
session    (id, idea_id, state, weights_json, started_at, ended_at)
turn       (id, session_id, seq, role, criterion, question_type, content)
evaluation (id, session_id, originality, practicality, acceptance,
            weighted_total, rationale_json, suggestions_json)
```

`turn.criterion`과 `turn.question_type`을 기록해 두면 "어떤 유형의 질문이
좋은 답변을 끌어냈는가"를 나중에 분석할 수 있다 — 시스템 자체를 개선하는 데이터가 된다.

### 4.4 채점 출력 스키마 (예시)

```json
{
  "originality":  { "specificity": 3, "consistency": 2, "self_awareness": 3,
                    "evidence": ["turn 7에서 기존 서비스 A와의 차이를 구체적으로 제시"] },
  "practicality": { "...": "..." },
  "acceptance":   { "...": "..." },
  "weighted_total": 7.4,
  "strengths": ["..."],
  "suggestions": ["...", "..."],
  "encouragement": "..."
}
```

모든 점수에 대화 턴 번호를 인용한 근거를 강제한다. 근거 없는 점수는 무효 처리.

## 5. 단계별 로드맵

| 단계 | 범위 | 검증 목표 |
|------|------|-----------|
| **1. 프롬프트 프로토타입** (1주) | 웹 없이 CLI/노트북에서 질문자·채점자 프롬프트만 실험 | 문답의 질. 여기서 6가지 질문 유형과 어조 규칙을 다듬는다 |
| **2. MVP 웹** (2~3주) | FastAPI + 단일 페이지 채팅 UI + SQLite. 로그인 없음 | 15분 세션을 끝까지 완주하는 사용자 비율 |
| **3. 평가 리포트** (1~2주) | 점수 대시보드, 대화 인용 근거 표시, 재도전 기능 | "점수에 납득하는가" 사용자 피드백 |
| **4. 운영 기능** | 가중치 설정, 다중 아이디어 비교, 관리자 뷰, 채점 일관성 검증(같은 로그 3회 채점 후 분산 측정) | 채점 신뢰도 |

## 6. 예상 리스크와 대응

- **제안자가 대화를 회피/장난** → 모호한 답변 2회 초과 시 해당 하위 지표 0점
  처리 규칙을 명시하고 UI에 사전 고지.
- **AI 질문이 공격적으로 느껴짐** → 어조 규칙을 시스템 프롬프트에 명문화하고,
  라운드마다 인정(acknowledgment)을 의무화. 파일럿에서 어조 피드백 수집.
- **채점 비일관성** → 채점자 호출을 temperature 0에 가깝게, 루브릭을 하위
  지표로 잘게 쪼개고, 동일 로그 반복 채점으로 분산을 모니터링.
- **반례 제시 시 할루시네이션** → 반례는 "~라는 지적이 가능하다" 형태의
  가설로만 제시하게 하고, 사실 단정을 금지. (장기적으로는 검색 연동)

## 7. 결론

웹 페이지로 구현 가능하며, 기술적 난이도보다 **문답 설계(3장)의 완성도**가
성패를 가른다. 따라서 웹 개발 전에 1단계 프롬프트 프로토타입으로 대화 품질을
먼저 검증하는 것을 권한다. 핵심 설계 원칙 세 가지를 다시 요약하면:

1. AI는 판결하지 않고 질문한다 — 점수는 답변의 질에서 나온다.
2. 약점 인정은 가점이다 — 솔직한 사고를 보상한다.
3. 질문자와 채점자를 분리한다 — 대화의 중립성과 채점의 설명 가능성을 확보한다.
