# kdinov — 정책 아이디어 신규성 검증 파이프라인

정책 아이디어가 실제로 새로운지를 KDI 및 국책연구기관 문헌에 대조해 판정한다.

## 설계 원칙

**검색을 위탁하지 않는다.** 이전 버전은 KDI 검색엔진에 질의를 던졌다.
그러면 재현율을 통제할 수 없다. 0건이 나왔을 때 그것이 '신규'인지
'그들의 토크나이저가 내 검색어를 못 쪼갠 것'인지 구별할 방법이 없다.
지금은 코퍼스를 로컬로 미러링하고 매칭을 직접 수행한다. 기본연구보고서와
현안자료를 합쳐 1,400건 수준이므로 미러링이 싸다. 부수 효과로 채점 규칙을
고쳐도 재수집이 필요 없어 반복 실험이 가능해진다.

**판정은 2차원이다.** 중첩의 정도(code)와 활용 방식(role)을 따로 낸다.
1차원으로는 쓸 수 없다는 것이 실행에서 드러났다. '수단축이 비었다'는
사실만으로는 그 문헌이 경합자인지 인용할 근거인지 알 수 없다.

| code | 의미 |
|---|---|
| N0 | 3축이 한 자리에서 일치. 신규 아님 |
| N1 | 축 하나가 상이하거나 3축이 흩어져 있음 |
| N2 | 축 하나만 강하게 겹침 |
| N3 | 영역만 중첩 |
| N4 | 무관 |

| role | 의미 | 대응 |
|---|---|---|
| 실행 | 법령·시행령·보도자료. 이미 제도화 | 신규성의 직접 반증. 아이디어 폐기 또는 재설계 |
| 경합 | 같은 수단을 이미 제안 | 차별화 논증 필요 |
| 근거 | 효과분석·현황진단만, 수단 제안 없음 | **인용해서 정당화에 쓴다. 가장 좋은 자리** |
| 선례 | 영역은 다르나 재원·전달체계 설계 참조 가능 | 설계 파라미터 벤치마크 |

`실행`을 별도 등급으로 분리한 것이 중요하다. 연구문헌은 '논의'지만
시행령은 '집행'이다. 신규성 검증에서 이 둘은 같은 무게가 아니다.

**아무것도 안 걸렸다는 결론은 재현율이 증명되기 전까지 무효다.**
`known_positives`에 손으로 미리 찾아 확인한 문헌을 적는다. 파이프라인이
이것을 표면화하지 못하면 종합 판정은 `VOID`가 되고 신규성을 주장할 수 없다.
코퍼스에 있는데 채점 규칙이 N4로 떨어뜨린 경우도 실패로 잡는다.

## 방향성 판정

오탐의 최대 원인은 축이 다 걸려도 정책의 화살표가 반대인 경우다.
`중소기업 지원정책에 AI를 적용`과 `중소기업에 AI 교육을 지원`은
대상·수단·영역이 모두 일치하지만 전자는 정부가 AI를 쓰는 이야기고
후자는 중소기업이 AI를 배우는 이야기다.

규칙은 원문 표면형에 정규식으로 적용한다. 형태소 단위로 하면
`인공지능`이 `인공/지능`으로 쪼개져 규칙이 발화하지 못한다.

| 규칙 | 패턴 | 판정 |
|---|---|---|
| B | 영역어 + 목적격 + 운용동사 (`AI 기술을 적용`) | 역전 |
| B2 | 영역어 + 행정작용 수식 (`AI 기반 정부 지원`) | 역전 |
| C | 대상어 + 정책/사업 (`중소기업 지원사업`) | 역전 |
| A | 영역어 + 수단어 복합 수식 (`AI 교육`) | 정렬 |
| D | 3축 + 이전동사 공기 | 정렬 |

역전 신호는 하나만 있어도 진단적이므로 상위 5개 창을 모두 보고
역전이 하나라도 있으면 역전으로 판정한다.

## 설치

```bash
pip install requests kiwipiepy pytest
```

kiwipiepy가 없어도 동작하지만 문장 분할이 정규식으로 퇴화한다.

## 사용

### 0) 응답 스키마 확인 — 반드시 먼저

`parse_archive`는 KDI Open API **문서에 적힌** 스펙대로 작성했고 합성
페이로드로만 검증했다. 실제 엔드포인트에 대해서는 확인하지 못했다.
필드명이 다르거나 전체목록 호출이 막혀 있을 수 있으므로 먼저 찍어본다.

```bash
export KDI_API_KEY=...        # kdi.re.kr/share/openAPI 에서 이메일 신청
python -m kdinov probe --cd A
```

`TOTAL_COUNT`가 1,300대로 나오고 `record keys`에 `PUB_NM_KORN`,
`SUMM_KORN`, `PUB_CN`이 보이면 정상이다. `ARCHIVE`가 짧게 잘려 오면
전체목록 호출이 막힌 것이므로 아래 `--terms` 경로를 쓴다.

### 1) 코퍼스 미러링

```bash
python -m kdinov mirror --cd AB --db kdi.sqlite
```

전체목록이 막혔을 때의 대체 경로. 이 경로는 재현율이 구성적으로
보장되지 않으므로 `known_positives` 통제를 반드시 통과해야 한다.

```bash
python -m kdinov mirror --terms --idea ideas/sme_ai_edu.json --db kdi.sqlite
```

### 2) 타 기관 자료 주입

**KDI 본체만으로 신규성을 판정하면 반드시 과대추정한다.** KDI는 정책을
만드는 곳이 아니라 평가하는 곳이다. 정책의 실재 여부는 다른 층위에 있다.

| 층위 | 소스 | 답하는 질문 |
|---|---|---|
| 담론·평가 | KDI Open API | 학술적으로 논의·평가됐나 |
| 정책 실재 | eiec.kdi.re.kr 경제정책정보 | 실제로 존재·추진 중인가 |
| 발주 이력 | PRISM, 중기연구원, KISDI, 입법조사처 | 이미 용역이 나갔나 |

아래 둘은 공개 API가 없으므로 JSONL로 주입한다. `tests/corpus.jsonl`이
형식 예시다.

```bash
python -m kdinov ingest --db kdi.sqlite --jsonl external.jsonl --source eiec
```

### 3) 후보 검색 — 네트워크 불필요, 판정 전 탐색

```bash
python -m kdinov search --db kdi.sqlite --idea ideas/sme_ai_edu.json --limit 20
python -m kdinov search --db kdi.sqlite --query "중소기업 AI 교육 무상 지원"
```

`--idea`는 축 정의·재원·전달체계 용어를 함께 써서 DB를 훑는다. 출력은 점수,
필드별 매칭, 근거 스니펫이다. 자유문 `--query`는 빠른 탐색용이고 정식 검증은
축 정의 파일을 쓰는 편이 안정적이다.

### 4) 판정 — 네트워크 불필요, 반복 실행 가능

```bash
python -m kdinov judge --db kdi.sqlite --idea ideas/sme_ai_edu.json -o report.md
```

종료코드 0은 정상, 2는 재현율 미달(VOID)이다. CI에 걸 수 있다.

### 5) 웹 페이지 — 브라우저에서 신규성·언급량 확인

```bash
python -m kdinov.web --db kdi.sqlite
python -m kdinov.web --demo
```

브라우저에서 아이디어와 축 용어를 입력하면 신규성 등급, 새로움 지수, 언급 후보 수,
직접 중첩 문헌 수, 역할별 분포와 근거 문헌을 한 화면에 보여준다. `--demo`는 테스트
코퍼스와 예술인 사례 코퍼스로 실행한다.

## 축 정의

```jsonc
{
  "idea": "중소기업에 AI 교육을 무상으로 지원",
  "axes": {
    "대상": { "exact": ["중소기업"], "syn": ["소상공인"], "broad": ["재직자"] },
    "수단": { "exact": ["교육","훈련"], "syn": ["인력양성"], "broad": ["지원"] },
    "영역": { "exact": ["AI","인공지능"], "syn": ["디지털 전환"], "broad": ["디지털"] }
  },
  "financing": ["무상","전액지원","자부담","매칭"],
  "delivery":  ["바우처","내일배움카드","위탁","세액공제"],
  "known_positives": ["손으로 찾아 확인한 문헌 제목"]
}
```

축 이름은 `대상`·`수단`·`영역` 세 개를 유지해야 한다. 방향성 규칙이
이 이름에 결합되어 있다. `financing`과 `delivery`는 판정을 바꾸지 않고
설계 차별화 여지를 알려준다 — 대상·수단·영역이 다 겹쳤을 때 아이디어가
살아남는 곳은 대개 여기다.

## 검증 상태

- `pytest tests/` 24건 통과. 각 케이스는 실제로 오판정이 났던 지점이다.
- 검증되지 않음: 실 API 엔드포인트에 대한 `mirror`/`probe`. 개발 환경의
  네트워크가 kdi.re.kr를 차단해 합성 페이로드로만 파서를 검증했다.
- 방향성 규칙은 규칙 기반이므로 재현율이 완전하지 않다. `불명` 판정이
  나온 건은 사람이 확인해야 한다. 그래서 보고서에 근거 문장을 항상 싣는다.

## 한계

축 용어집을 사람이 만든다. 이것이 이 시스템의 실질적 상한이다.
`중소기업`의 동의어에 `영세사업자`를 넣지 않으면 그 문헌은 안 걸린다.
`known_positives` 통제가 이 실패를 잡아주지만, 통제 자체도 사람이
손으로 찾은 것이라 완전하지 않다. 판정을 최종 답이 아니라 검토 대상
목록으로 취급하는 것이 맞다.
